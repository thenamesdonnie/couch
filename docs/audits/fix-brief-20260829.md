## 1. CRITICAL - inputproc caches input ownership at startup

`grants_input()` is called once, in `main()` (`couchd/inputproc.py:1411`), and
`self.own` is set from it in `__init__` (`:549`). The main loop re-reads gesture
settings every pass (`:1303`) but never re-reads `owns.conf`.

Consequence: removing `input` from `owns.conf` does not release the pad. A
running inputproc keeps `EVIOCGRAB` and keeps withholding `BTN_MODE`. Because
axes and other buttons still pass through the virtual pad, this presents as a
*selectively dead PS button*, not as a dead service. The documented rollback
lever is inert.

Required: make the ownership interlock continuous. When `input` is withdrawn,
or the supervisor connection is lost beyond the existing lease grace, the
process must atomically clear pending gesture state, reset the tracker, ungrab
the physical device, set `self.own = False`, and fall back to the existing
observe-and-forward path. It may only re-acquire when ownership AND supervisor
connectivity are both restored, and it must take a fresh button baseline when
it does, so a button held across the transition cannot synthesise an event.

Re-read cost matters: this is a hot loop. `gestureconf.load()` is already a
`stat()` unless the file changed - use the same pattern rather than reading and
parsing `owns.conf` every pass.

## 2. HIGH - configured gesture timings never reach couchd's classifier

`couchd/couchd.py:3701` constructs `gesture.PressTracker()` with **no
arguments**, so it runs on hard-coded defaults. `couchd/inputproc.py:551`
constructs the same class *with* the loaded config. Separately,
`couchd.py:~5277` does pass live `hold_seconds` into `Observed` every pass.

So the object that actually classifies tap vs hold is the one that never learns
the user's timings. Some guards also call `is_tap()` without the configured
threshold (`couchd.py:674`, `couchd.py:779`).

Required: couchd's tracker must be configured from the same loaded settings
inputproc uses, and must pick up changes. Update timings only while no press is
in flight, and snapshot the timings for the lifetime of a given press so a
reload mid-press cannot reclassify it. Pass the configured threshold to every
tap predicate rather than letting defaults leak in.

Add a test that exercises the couchd runtime path with NON-default timings.
Today's defaults mask this entirely, which is why the existing suite passes.

## 3. HIGH - the PS-button switcher path shows Kodi with nothing covering it

In the bare-X11 (non-gamescope) branch the order is: freeze the game, route the
pad, raise Kodi, spawn the guard, and only then
`Addons.ExecuteAddon script.couch.switcher` (`couchd/couchd.py:~3499`, intents
built around `:1789-1845`). A comment in that same file measures the addon at
**1.3-1.5 seconds** to draw. Nothing covers that window, so Kodi Home is on
screen for well over a second. This is the user's reported symptom.

Note `tools/curtain` exists for exactly this and `couchd.py` never invokes it:
all 25 `curtain` references in that file are observational (`curtain_on_top`,
`g_fg_curtain`, reading order).

Required: no Kodi frame may reach the screen on this path. Prefer keeping the
frozen game visible while the addon starts behind it, then swapping once the
switcher window is confirmed present, over raising a curtain, because it needs
no extra process. If you do use the curtain, it must be confirmed up before
Kodi is raised. Either way the swap must be driven by positive confirmation
that the switcher window exists, not by a sleep.

Respect the existing ordering rule and the `g_tap_resume_due` fix; do not
reintroduce the resume-after-tap bug. Keep the gamescope rail branch working.

## 4. HIGH - a retiring launcher stamps on the next launch's curtain

`legacy-mirror/game-launch`: the EXIT trap removes the session flag **only if
this shell owns it** (`[ "$(cut -d' ' -f1 "$SESSION")" = "$$" ]`), with a
comment explaining that an old launcher must not take a new launcher's flag.
But `restore_on_exit` is then called **unconditionally**, and it does
`pad_to_kodi; focus_kodi; curtain_fade`.

Meanwhile a fresh launch calls `curtain_show_loading` (~`:1408`) *before* it
claims the session (~`:1422`), so there is a window where the new curtain is up
and the session flag still names the old launcher.

Consequence: an exiting launcher raises Kodi and fades the incoming launch's
curtain. That is the visible flip on game launch.

Required: extend the ownership guard that already protects the flag to cover
the screen restore beside it. A launcher that no longer owns the session must
not call `focus_kodi` or `curtain_fade`. Close the ordering gap so a new
launcher's curtain is never attributable to the old one - publish the new
launcher's generation before showing its curtain, or claim the session first.
Do not hold a lock for the game's lifetime.
