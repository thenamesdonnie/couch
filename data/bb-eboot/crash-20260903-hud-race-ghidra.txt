BLOODBORNE 1.09 (shadPS4) CRASH CHAIN REPORT
GXRenderThread / DLLightMutex "Mutex is not initialized" -> fault at 0x1f591c7
Ghidra project ~/src/bb-ghidra, program "full", bb109.elf, image base 0.
Guest 0x8xxxxxxxx == Ghidra 0xxxxxxxx (all addresses below are module VAs).

--------------------------------------------------------------------------------
0. SUMMARY IN ONE LINE
--------------------------------------------------------------------------------
The GX render thread was executing a queued Scaleform/GFx draw command for the
HUD movie "playerstatus_equipment.gfx". The command handler tried to take the
GLOBAL DLLightMutex of the Scaleform work-dispatch singleton at VA 0x5594200,
that mutex reported itself uninitialised (its DAT_05594210 flag was 0), the
underlying scePthreadMutexLock then returned EINVAL, and because DL_PANIC is
not "noreturn" in this build the handler carried on WITHOUT the lock and
immediately dereferenced a stale pointer field (movie+0x940) belonging to a
GFx movie object that the scene transition had already torn down. The faulting
instruction is a vtable load for a virtual call.

2. LIVE FRAMES vs STALE FRAMES
--------------------------------------------------------------------------------
The supplied list cannot be a pure call chain. Frame (4)'s return address
follows a call to a memcpy (FUN_0261a1b0), and a memcpy cannot be the caller
of frame (3). Likewise frame (7) is inside DLConditionSignal::SetSignal, which
only calls pthread wrappers and DL_PANIC and cannot reach frame (6).
What the list actually is, is a scan of the render thread's stack that picked
up both live frames and leftovers from calls that had already returned at the
same stack depth. Reconstructed:

  LIVE:
    0x263b246   DLThreadHandle trampoline
    0x21b69d5   GXRenderThread loop, at `CALL FUN_02199af0`
    0x2199bbe   FUN_02199af0, at `CALL FUN_021b4d00`
    0x21b4dca   FUN_021b4d00, at `CALL qword ptr [RBX]`  <- the render command
    (then the command thunk at 0x1f644d0, which TAIL-JUMPS, so it leaves no
     frame of its own, into FUN_01f59150 where the fault happened)

  STALE, in stack order:
    0x207e8a7   leftover of `FUN_0207e780(this+0x48, 0)` at 0x21b69bd, made
                11 bytes before the live FUN_02199af0 call
    0x2198f1a / 0x21a1d7c / 0x21a1f45 / 0xe46de7
                leftovers of the FUN_02198c10 "begin frame" descent that
                FUN_02199af0 made at 0x2199ba9 and that had already returned

This matters for triage: the PthreadMutex.cpp 130/132/134 trio in the log did
NOT come from frame (7). It came from the live path, see section 3.

4. THE CRASH SITE: FUN_01f59150 (0x1f59150 - 0x1f592c6)
--------------------------------------------------------------------------------
0x1f591c7 is inside FUN_01f59150. Disassembly around it:

  01f5919b  CALL 0x0207ee90        ; DLLightMutex::Lock(&DAT_05594200)  <-- PANIC
  01f591a0  LEA  R15,[RBX + 0x38]
  01f591a4  MOV  RAX,[RBX + 0x38]
  01f591ad  MOV  RDI,R15
  01f591b0  CALL [RAX + 0x18]      ; second lock, this+0x38, vtable Lock
  01f591b3  MOV  RAX,[RBX + 8]     ; RAX = the GFx movie object
  01f591b7  MOV  RDI,[RAX + 0x940] ; RDI = movie->m_something
  01f591be  TEST RDI,RDI
  01f591c1  JZ   0x01f591fd        ; <-- null is EXPLICITLY handled
  01f591c3  LEA  R12,[RBX + 0x30]
  01f591c7  MOV  RAX,[RDI]         ; <== FAULT: load the vtable pointer
  01f591ca  CALL [RAX + 0x98]      ; virtual call

Note the guard at 0x1f591be/0x1f591c1: if RDI were NULL the code would have
branched away. So this is NOT a "deliberate null read" and it is not DL_PANIC's
abort (DL_PANIC is FUN_020b55b0, 0x20b55b0-0x20b5841, and it does not contain
this address; it logs and returns). It is a genuine USE AFTER FREE: RDI was a
non-null pointer into memory that had already been released, so the vtable load
faulted.

At 0x1f644d0 there is a three-instruction render-command thunk:

  01f644d0  TEST RDX,RDX / JZ 0x01f644dd
  01f644d5  MOV RDI,RDX
  01f644d8  JMP 0x01f59150                      ; command thunk B  <-- ours
  01f644dd  RET

Its only producer is FUN_01f5c1b0 (0x1f5c1b0 - 0x1f5c79f), the SprjGraphics
draw-dispatch on the game/main side:

  FUN_021b4b00(commandList, &LAB_01f644d0, param_1, item, 0xffffffff);

FUN_01f5c1b0, in words: assert the SprjGraphics FD4 singleton (DAT_05540190),
tick the frame, release the old work reference, queue thunk A (0x1f644c0 ->

handle) snapshot the active movie list at this+0x990 (a DLFixedVector capped at

6. QUESTION 2: THE THREE "VTABLES"
--------------------------------------------------------------------------------
Checked directly. 0x5699e68, 0x569b628 and 0x569b6d0 are NOT vtables, and they
cannot be: the eboot's RW segment is file-backed only to VA 0x53e5b38, and .bss
runs from there to 0x56d30f4. All three addresses are in .bss, i.e. zero on
disk and filled at runtime. They are also not code-adjacent - PtrsAt on each
returns only zeroes.

What they really are: slots inside two large global singleton objects built by
the C++ static-initialiser block at 0x1fc2600-0x1fc2d00. The pattern, twice:

  LEA R12,[0x5358b60]  ; class vtable
  MOV [0x5699e48],R12  ; <- object A base = 0x5699e48
  LEA R13,[0x53aefa0]  ; sub-object vtable
  MOV [0x5699e68],R13  ; <- base+0x20, the EMBEDDED sub-object's vptr slot
  LEA RDI,[0x5699e70]; memset(RDI, 0, 0x448)
  ... scePthreadMutexInit(0x569a2c8, ..., spin 0x30d40)
      on failure: DL_PANIC("...CSPlainAdaptiveMutexImp_sce.cpp", 0x51,
                           "DLAdaptiveMutex initialization error")

  identically for object B: base 0x569b608, vtable slot 0x569b628 = base+0x20,
  memset from 0x569b630 size 0x448, DLAdaptiveMutex at 0x569ba88.
  0x569b6d0 = 0x569b628 + 0xa8, i.e. inside that memset region - it is a plain
  field of object B, nothing in the binary references it directly.

The class: vtable 0x5358b60, destructor FUN_01fc5ac0. That destructor frees the
backing buffer through an allocator interface (`allocator->vtable[0x70](alloc,
ptr)`), zeroes a 0x400-byte table of 16-byte entries, then finalises its
DLAdaptiveMutex ("DLAdaptiveMutex finalization error. Maybe it's still locked.",
CSPlainAdaptiveMutexImp_sce.cpp line 0x5d). Sibling class at 0x53b1ab0 /
FUN_01fc63a0 is the smaller variant.
So: these are the game's GLOBAL ALLOCATORS / HEAPS - Dantelion DLAllocator-style
objects with a 64-entry free-list table guarded by a DLAdaptiveMutex - not any
GFx, Movie, PlayerStatus, SprjMenu or DLLightMutex class. There are no RTTI
typeinfo records to read (the binary is built with RTTI off; the class identity
above comes from the CSPlainAdaptiveMutexImp / DLAdaptiveMutex assert strings
in the same basic block).

CONSEQUENCE FOR THE DUMP READING: a heap object whose qword reads 0x5699e68 or
0x569b628 is almost certainly carrying an ALLOCATOR BACK-POINTER (the standard
Dantelion `m_allocator` member that FD4/DL objects store next to the vptr), not
a vtable pointer. That is consistent with everything else here: the objects at
r13 = 0x20008cd20, at rax+0x40 and at 0x3e26cdbc0 are ordinary heap objects
tagged with which global heap they came from. It also means those values tell
us nothing about the crash and should not be chased further.
(For contrast, the one REAL vtable in this crash is 0x53b2fa0, DLLightMutex,
listed in section 3.)

7. QUESTION 3: WHAT THE RENDER THREAD WAS DOING - the reading
--------------------------------------------------------------------------------
The render thread was draining the frame's GX command list and reached the
per-movie Scaleform draw command that the game thread had queued from
FUN_01f5c1b0 for the equipment HUD movie "playerstatus_equipment.gfx". That
handler, FUN_01f59150, wants the process-wide Scaleform dispatch lock - the
DLLightMutex at 0x5594200 that guards the ScaleformTexRepository/SprjGraphics
work objects, the same lock under which FUN_01f62ae0 allocates and FUN_01f62e30
retires the 0x980-byte movie-render objects. That lock answered "not
initialized" (its DAT_05594210 flag was 0) and the emulated scePthreadMutexLock
then answered EINVAL, so the whole critical section ran UNSERIALISED, and one
instruction later the handler read `movie->[0x940]`, a field that the tear-down
side had already freed and that the null guard could not catch because the
pointer was stale rather than nulled. This is a game-thread versus render-thread
LIFETIME RACE, not a rendering bug: the head-armour equip plus the
remo/s25_00_0010 cutscene transition (with chr/c0000.chrbnd.dcx reloaded)
destroyed and rebuilt the equipment HUD movie and its GFx texture bindings on
the game thread while the render thread still held a command referencing the
old instance, and the mutex that exists precisely to prevent that overlap was
not usable at the moment it was needed. Two things can leave 0x5594210 at zero:
the singleton's static destructor FUN_01f37180 having run (a shutdown or
re-init of the Scaleform layer), or the original scePthreadMutexInit in
FUN_01f36d40 having failed while __cxa_guard_release still marked the singleton
as constructed - and under an emulator the second is the more suspicious of the
two, because a host-side pthread failure would leave every later Lock and
Unlock on that global silently no-op, which is exactly the condition needed to
turn a normally-safe teardown into this use-after-free. Practically: this crash
signature is "HUD/Scaleform object destroyed underneath a queued render command
during a scene transition", it will reproduce around scene transitions that
rebuild the HUD, and it is unrelated to the movement or camera work.

c) Code caves 0x50db000-0x50db400: I enumerated every reference to every byte
